# PetalPath Engineering Rules

## Priority Resolution Order
1. User instructions (highest priority)
2. Repository documentation
3. Existing codebase patterns
4. AGENTS.md
5. AI assumptions (never construct changes based on assumptions)

---

## 1. Scope of Edits & Discipline

*   **Zero-Churn Policy**: Modify ONLY files directly related to the current task. Do not perform speculative refactoring, cleanups, modernizations, folder reorganization, or symbol renames in adjacent modules unless explicitly requested.
*   **Minimal Change Principle**: Implement the smallest change that fully satisfies the request. Avoid introducing new abstractions, dependencies, or architectural changes unless they are clearly required.
*   **Search Before Creating**: Before implementing any utility, hook, service, repository, component, or store, search the repository first to check for existing solutions or helpers.
*   **Cohesive Functions**: Prefer small, single-purpose functions. Refactor to split functions only when it clearly improves readability, testability, or maintainability. Do not split functions simply to satisfy arbitrary line counts.
*   **Preserve Metadata**: Keep all existing comments, docstrings, inline annotations, and lint suppressions unless they are directly invalidated by your edits.

---

## 2. Technical Philosophy & Safety

*   **Extension Over Abstraction**: Extend existing systems and tools rather than introducing new ones. Prefer consistency and predictability over novelty or cleverness.
*   **Backward Compatibility**: Unless explicitly requested, preserve existing APIs, data contracts, navigation flows, and public interfaces. Avoid breaking changes.
*   **Do Not Guess (No Inventions)**: Never invent or assume APIs, database fields, routes, environment variables, configs, or business rules. Search the codebase first; if still uncertain, ask the user.
*   **Access Control**: Any resource scoped to a parent or child entity must enforce ownership or authorization before access.
*   **Transaction Safety**: Any logical operation that must succeed or fail atomically should execute within a database transaction.
*   **Credential Protection**: Never commit or hardcode credentials, secrets, or raw API keys. Retrieve them via environment variables.

---

## 3. Responsive Screen Layout Rules

*   **Responsive Screens**: Do not split a single new screen file into multiple duplicative viewport screen files (e.g. ScreenMobile, ScreenTablet, ScreenDesktop). Instead, use responsive components and hook-based viewport configurations in a single unified screen.
*   **Extraction Threshold**: Extract specific viewport sub-components only when layout complexity requires it.

---

## 4. Verification & Validation Rules

*   **Scope-Appropriate Validation**: Run the appropriate validation for the scope of the change. Documentation changes require link validation only. Code changes require compilation and relevant tests.
*   **Use Project Commands**: Use documented project commands. If documentation is missing, ask before proceeding.
*   **Destructive Protections**: Never run or propose commands that reset databases, purge migrations, or wipe persistent stores unless explicitly requested.

---

## 5. Definition of Done (DoD Checklist)

A task is complete only when:
- [ ] Relevant code compiles without errors.
- [ ] Relevant tests pass.
- [ ] No unrelated files or directories were modified.
- [ ] Coding conventions and patterns of the existing codebase were followed.
- [ ] Documentation is updated whenever behavior, architecture, configuration, or public interfaces change.
- [ ] No duplicate logic or duplicate dependencies were introduced.
- [ ] No new warnings or lint errors are introduced without explanation.

## 6. Coding Patterns Baseline

### Database Access

```typescript
// ❌ BAD: Direct database queries inside endpoint handlers, bypassing encapsulation and authorization
async function completeAction(req, res) {
  const { resourceId, ownerId } = req.body;
  const result = await database.item.create({ data: { ownerId, itemId: resourceId } });
  return res.json(result);
}

//   GOOD: Query logic encapsulated in dedicated access layers with authorization checks applied
// In modules/resource/resource.repository.ts
export class ResourceRepository {
  async completeItem(ownerId: string, id: string) {
    return database.item.create({
      data: { ownerId, itemId: id }
    });
  }
}
// In modules/resource/resource.routes.ts
router.post('/resource/:ownerId/complete', authenticate, verifyOwnership, controller.complete);
```

## 7. Success Criteria

The best implementation is one that:
*   Solves the requested problem.
*   Introduces the least necessary change (Minimal Change).
*   Preserves existing architecture and style patterns.
*   Is easy for the next engineer to understand.
*   Requires minimal future maintenance.
